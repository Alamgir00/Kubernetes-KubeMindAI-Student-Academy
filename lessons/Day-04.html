2. Concepts and Technical Explanations

ReplicaSet

Maintains a desired number of matching Pods.

Deployment

Manages ReplicaSets and provides declarative application updates.

Rolling update

Gradually replaces old Pods with new Pods.

Revision

A recorded Deployment rollout version.

Rollback

Returns a Deployment to a previous revision when available.

Complete backend lifecycle of kubectl apply -f deployment.yaml

Key distinction: a successful apply confirms that the API operation was accepted. It does not guarantee that the Deployment has completed rollout or that its Pods are Ready.

1. Client-side processing and API request

  1. Read and parse: kubectl reads the YAML document, decodes the Kubernetes object, resolves API group/version/kind, namespace and resource name.
  2. Context and identity: kubectl loads kubeconfig, selects current context, endpoint, trust bundle and authentication method. Credential plugins may obtain short-lived cloud identity tokens.
  3. Discovery and REST mapping: kubectl discovers the API resource and maps Deployment to the namespaced apps/v1 endpoint.
  4. Apply calculation: client-side apply calculates a patch using the manifest and last-applied-configuration annotation. Server-side apply sends an apply patch and lets the API server manage field ownership in managedFields.

2. API server request pipeline

  1. Authentication: API server establishes the caller identity (for example certificate, bearer token or webhook / external identity integration).
  2. Authorization: configured authorizer checks whether the identity can perform the requested verb on Deployments in the namespace. RBAC is commonly used.
  3. Mutating admission: applicable admission plugins / webhooks can default or mutate the object.
  4. Schema and API validation: object fields, types, required values and API invariants are checked.
  5. Validating admission: applicable policy webhooks / admission plugins can reject an otherwise valid request.
  6. Field management and conflict checks: server-side apply tracks field ownership; conflicting field managers can produce a conflict response.
  7. Persistence: accepted object is stored in the API server backing store (etcd in standard Kubernetes control planes), then the API response returns to kubectl.

3. Asynchronous control loops

  1. Deployment controller: observes the Deployment and creates or updates a ReplicaSet for the Pod template revision.
  2. ReplicaSet controller: compares desired replicas with matching actual Pods and creates or deletes Pod API objects to converge.
  3. Scheduler: watches unscheduled Pods, filters and scores eligible nodes using requests, taints/tolerations, affinity, topology and policies, then binds a Pod to a node.
  4. Kubelet: on the selected node, observes assigned Pod, prepares volumes and networking, and calls the CRI runtime.
  5. CRI runtime + CNI: runtime creates Pod sandbox and containers; CNI plugin configures Pod networking as part of sandbox setup.
  6. Probes: startup probe gates liveness/readiness while configured; liveness can trigger container restart; readiness controls traffic eligibility.
  7. EndpointSlice controller + Service dataplane: EndpointSlices reflect eligible Pod endpoints; kube-proxy or an eBPF dataplane routes Service traffic to them.

Example manifest with important fields

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: default
spec:
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80
        readinessProbe:
          httpGet: { path: /, port: 80 }
          initialDelaySeconds: 3
          periodSeconds: 5

Field interpretation: apiVersion/kind select the API schema; metadata identifies the object; replicas is desired count; selector must match Pod-template labels; template is copied into created Pods; container image and probe define runtime behaviour.

Interview questions with concise answers

  • Does apply mean Pods are ready? No. It confirms API acceptance; controllers, scheduler and kubelet reconcile asynchronously.
  • Which controller creates ReplicaSets? Deployment controller. ReplicaSet controller creates / deletes Pod objects.
  • Who selects the node? kube-scheduler; kubelet manages the Pod after binding.
  • What is server-side apply? API-server-managed field ownership and merge semantics, recorded in managedFields.
  • How does readiness affect traffic? Readiness status influences EndpointSlice membership for Service backends.
  • Where is desired state stored? In the API server backing store, typically etcd.

5. YAML Example

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
        ports:
        - containerPort: 80

Review the API version, kind, metadata, selectors, labels, Pod template and container configuration. Save the example as a YAML file before applying it. Adapt placeholders to your environment.

8. Troubleshooting Scenarios

ProgressDeadlineExceeded: inspect Pod events and readiness. Old Pods remain: inspect rollout strategy and availability. Rollback does not restore external database changes; treat migrations separately.

Structured troubleshooting method

  1. Identify the scope and customer impact.
  2. Capture Pod status, node status and events.
  3. Inspect resource descriptions and logs.
  4. Compare the current state with the desired configuration.
  5. Check recent changes and dependencies.
  6. Apply a controlled correction.
  7. Verify recovery and document the root cause.

9. Production Considerations

  • Use least privilege and protect credentials.
  • Use resource requests and limits where appropriate.
  • Validate changes in a non-production environment.
  • Monitor application health and infrastructure health.
  • Maintain backups for important stateful data.
  • Document ownership, recovery and rollback procedures.
