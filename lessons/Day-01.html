2. Concepts and Technical Explanations

Kubernetes

An open-source platform for deploying, scaling and managing containerized applications.

API Server

The Kubernetes API entry point. It processes authentication, authorization, admission and resource requests.

etcd

The key-value data store used for Kubernetes cluster state.

Scheduler

Selects a suitable node for an unscheduled Pod.

Controller Manager

Runs controllers that reconcile actual state toward desired state.

Kubelet

Node agent that manages assigned Pods and reports node and Pod status.

Container Runtime

Runs containers through the Container Runtime Interface.

kube-proxy

Traditionally implements Service networking behavior on nodes; some network plugins replace this function.

  1. kubectl loads kubeconfig and selects context
  2. Client discovers the target API resource
  3. API server authenticates the caller
  4. Authorization and admission policy checks run
  5. API server validates and persists API objects
  6. Controllers reconcile desired state
  7. Scheduler binds Pods to nodes
  8. Kubelet and runtime start containers
  9. Networking and readiness make workloads reachable
Failure checkpoint: API server unavailable or etcd unhealthy
Recovery path: Check control-plane health and API endpoint reachability; restore control-plane dependencies before retrying workloads.

5. YAML Example

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: payment
  template:
    metadata:
      labels:
        app: payment
    spec:
      containers:
        - name: payment
          image: nginx:1.27
          ports:
            - containerPort: 80

Review the API version, kind, metadata, selectors, labels, Pod template and container configuration. Save the example as a YAML file before applying it. Adapt placeholders to your environment.

6. Hands-on Practical Lab

Inspect the cluster; identify control-plane and worker nodes; create the Deployment; watch its Pods; delete one Pod and observe the Deployment controller create a replacement.

Suggested lab sequence

  1. Verify your current Kubernetes context.
  2. Inspect existing resources before changing anything.
  3. Create the lab resources using the supplied YAML.
  4. Watch the resource status and Kubernetes events.
  5. Test the expected behavior.
  6. Record the output and explain what happened.
  7. Clean up only resources created for this exercise.

7. Verification and Expected Results

kubectl apply -f payment.yaml; kubectl get deployment payment-service; kubectl get pods -l app=payment -o wide; kubectl describe deployment payment-service.

Success means the expected resource state and behavior are visible. A command returning successfully is not sufficient if the workload is not healthy.

8. Troubleshooting Scenarios

Pending Pod: inspect scheduling events, resources, selectors and taints. ImagePullBackOff: inspect image name, tag, registry access and pull credentials. API Forbidden: inspect the active identity and RBAC permissions.

Structured troubleshooting method

  1. Identify the scope and customer impact.
  2. Capture Pod status, node status and events.
  3. Inspect resource descriptions and logs.
  4. Compare the current state with the desired configuration.
  5. Check recent changes and dependencies.
  6. Apply a controlled correction.
  7. Verify recovery and document the root cause.

9. Production Considerations

  • Use least privilege and protect credentials.
  • Use resource requests and limits where appropriate.
  • Validate changes in a non-production environment.
  • Monitor application health and infrastructure health.
  • Maintain backups for important stateful data.
  • Document ownership, recovery and rollback procedures.
