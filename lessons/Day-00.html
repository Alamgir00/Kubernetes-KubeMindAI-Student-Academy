1. Learning Objectives

  • Prepare a reliable learning environment
  • understand local versus cloud Kubernetes
  • install and verify the command-line tools
  • prepare two Ubuntu EC2 instances for a self-managed kubeadm cluster.
Study the concepts first, then perform the lab in a disposable training environment. Understand every command before running it.

2. Concepts and Technical Explanations

Local environment

Your Mac is the administration workstation. You use its terminal, kubectl, SSH and browser to manage Kubernetes.

kubectl

The Kubernetes command-line client. It sends API requests to the cluster configured in your kubeconfig.

kubeconfig

A configuration file containing cluster endpoints, credentials and contexts. Treat it as sensitive.

Local cluster

Kind or Minikube is useful for quick exercises. It is not the same as two independent EC2 machines.

AWS lab

Two Ubuntu EC2 instances in one VPC will be used for the self-managed kubeadm cluster: one control plane and one worker.

# Check or install command-line tools using official vendor instructions

# Check SSH

# After downloading your EC2 key, restrict its permissions

Run commands in the correct cluster context and namespace. Replace example names with the actual names returned by your cluster.

5. YAML Example

# Example SSH configuration on your Mac: ~/.ssh/config
Host k8s-control
    HostName CONTROL_PLANE_PUBLIC_IP
    User ubuntu
    IdentityFile ~/Downloads/kubemindai-key.pem

Host k8s-worker
    HostName WORKER_PUBLIC_IP
    User ubuntu
    IdentityFile ~/Downloads/kubemindai-key.pem

Review the API version, kind, metadata, selectors, labels, Pod template and container configuration. Save the example as a YAML file before applying it. Adapt placeholders to your environment.

6. Hands-on Practical Lab

On the Mac, verify Python, Git, Docker, kubectl and Helm. Install each using its official vendor instructions. In AWS, create a VPC with a private subnet and suitable route/NAT design. Launch two Ubuntu Server 24.04 LTS x86_64 EC2 instances in the same VPC. Record private IPs. Restrict SSH to approved administrator IPs. Permit Kubernetes API traffic only from trusted cluster sources. Permit kubelet and Flannel VXLAN traffic only between cluster nodes. Install containerd and kubeadm prerequisites on both nodes. Initialize the control plane, install Flannel, join the worker and verify both nodes become Ready. This is a learning cluster, not a highly available production design.

Suggested lab sequence

  1. Verify your current Kubernetes context.
  2. Inspect existing resources before changing anything.
  3. Create the lab resources using the supplied YAML.
  4. Watch the resource status and Kubernetes events.
  5. Test the expected behavior.
  6. Record the output and explain what happened.
  7. Clean up only resources created for this exercise.

7. Verification and Expected Results

On Mac: uname -m; python3 --version; git --version; docker --version; kubectl version --client; helm version. On EC2: hostnamectl; ip -br address; systemctl status containerd; systemctl status kubelet. After cluster setup: kubectl get nodes -o wide; kubectl get pods -A.

Success means the expected resource state and behavior are visible. A command returning successfully is not sufficient if the workload is not healthy.

8. Troubleshooting Scenarios

SSH timeout: inspect routes, public access path, security groups and NACLs. Permission denied: check key path, chmod 400 and Ubuntu username. kubeadm preflight error: inspect swap, kernel modules, sysctl, ports and runtime configuration. Worker NotReady: verify Flannel, private IP reachability, containerd and kubelet. Do not expose etcd or kubelet publicly. Keep the kubeconfig and SSH private key confidential.

Structured troubleshooting method

  1. Identify the scope and customer impact.
  2. Capture Pod status, node status and events.
  3. Inspect resource descriptions and logs.
  4. Compare the current state with the desired configuration.
  5. Check recent changes and dependencies.
  6. Apply a controlled correction.
  7. Verify recovery and document the root cause.

9. Production Considerations

  • Use least privilege and protect credentials.
  • Use resource requests and limits where appropriate.
  • Validate changes in a non-production environment.
  • Monitor application health and infrastructure health.
  • Maintain backups for important stateful data.
  • Document ownership, recovery and rollback procedures.
